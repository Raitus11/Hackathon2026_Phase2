# Q&A — cold answers (after the slot)
- **Alias or what?** "A remote queue definition, not an alias — QREMOTE under the identical name the producer opens, RNAME pointing at the dedicated target QM via a triggered transmission queue and sender channel. The application's MQOPEN and MQPUT are bit-identical; the change lives entirely in MQ name resolution."
- **Channels — provisioning or migration?** "Two channel sets, two phases: the new estate's internal mesh is built during staging, touching only net-new QMs; the source-to-target bridge — both legs — is built at cutover, the single heritage reconfiguration, gated behind the approval click."
- **Really zero downtime?** "Zero application downtime — no reconnect, redeploy, or config change — with the message-path cutover executed as a single MQSC batch; a PUT resolves to the old queue pre-batch or the remote definition post-batch."
- **And if the DEFINE half of your batch fails?** "Rollback inverts the cutover step unconditionally — DELETE the remote if present, redefine the local queue — so the source queue is restored regardless of how far the batch got. The inverse is idempotent by construction."
- **Drain guarantee?** "After rewiring, arrivals to the old queue are zero, so it only empties; Little's Law predicts the drain and a gate requires depth zero plus zero input and output handles across three consecutive polls before any delete. Gate timeout → automatic rollback with the original queue intact; in-transit messages persist on the triggered XMITQ with a DLQ backstop on every QM."
- **A PUT at the exact cutover instant?** "Exposure is one in-process MQSC batch — the message resolves to the old local queue before it or the remote definition after it; the queue was drained to zero under the gate first, so nothing stored was ever at risk."
- **Rollback itself fails?** "ROLLBACK_FAILED and stop — we never roll back a rollback; the audit log shows exactly which inverse failed and the runbook resumes from a known state."
- **Channel auth on the bridges?** "Production deployments apply explicit per-peer channel-authentication rules — peer DN and address maps — generated by the same control plane that generates everything else." *(If pressed: "not on this non-prod demo estate; the production posture is the per-peer rules, emitted by the same governed path.")*
- **Mainframe apps?** "The rewiring is transparent at the MQ layer, so any app whose messages traverse these queue managers benefits regardless of where it runs; execution on z/OS itself is outside this control plane's boundary — we govern the distributed MQ estate."
- **When is this the wrong tool?** "When an application hardcodes the queue-manager name rather than the queue name, when a global XA transaction spans the cutover instant, or when the work is z/OS execution itself. Inside transparent MQ-layer rewiring we're strong; outside that boundary we say so."
- **Why not IBM MQ Operator?** "The Operator manages QM lifecycle but abstracts away the per-command MQSC trail we need to prove and reverse every change; our control plane keeps every operation explicit, governed, audit-logged, and individually reversible."
- **Scale?** "Each app is an independent run, so the work factorizes and the control plane is stateless against its database; at large scale the DB write rate is the real bottleneck — partitioned per app, not by changing the migration mechanics."
