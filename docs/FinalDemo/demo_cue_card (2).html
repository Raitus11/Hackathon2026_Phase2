Rapid Q&A viva
How is this different from stop-and-restart?
Stop-and-restart = downtime, lost in-flight messages, app reconfig, coordinated outage. We move it running via the in-place QREMOTE swap — none of those. The whole point for a critical app.
In-flight messages at cutover?
Not deleted until provably empty — depth/IPPROCS/OPPROCS all zero over three polls. In-transit rides the bridge; bridge torn down last so nothing is stranded.
How do you know co-tenants aren't disturbed?
Enumerate every command, gate on zero touching a neighbour's exclusive queue. Co-tenants re-routed transparently, no reconfig.
Step fails mid-migration?
Engine → ROLLING_BACK, walks steps in reverse Lamport order executing each captured inverse on the same QM; bridge last; per-app local — never touches another app.
Why MQSC via oc exec, not the K8s/MQ Operator?
K8s API for the platform (pods, PVCs, secrets, services); MQSC for messaging objects — they're MQ-internal, not K8s concepts. MQSC gives the exact command text for the audit log and evidence. The Operator would abstract that away and we'd lose the command-level trail.
Little's Law — how?
At cutover the producer is rewired away, λ≈0, so L=λW reduces to T_drain ≈ L₀/μ (L₀ = depth at rewire, μ = consumer rate measured during channel-up). We predict, then verify by polling to zero. (If L₀=0 on screen: no buffered messages, drained instantly; mechanism identical at any depth.)
Markov — how's the probability computed?
State machine as an absorbing chain. Fundamental matrix N=(I−Q)⁻¹ → expected steps to absorption. Absorption probabilities B=N·R → P(end in COMPLETED / ROLLED_BACK / ROLLBACK_FAILED), columns sum to 1. That's the reference model; shown beside the empirical estimate counted from the real audit log. Never blended.
Lamport — why, for auditing?
Wall-clock can tie/skew across components; Lamport clocks give unambiguous causal order — if A precedes B, A's clock < B's. Replay and rollback order by Lamport, not wall time. Rollback walks steps in reverse Lamport order. (Lamport, 1978.)
Why SQLite?
Single control-plane instance, migrations serialized — ACID, zero-ops, file-backed system of record. SQLAlchemy schema, so Postgres is a connection-string change when we need HA and concurrent operators. Deliberate scope choice, not a limit.
Why PVCs and secrets?
Real queue managers. PVC = durable storage at /mnt/mqm so queue data and persistent messages survive a pod restart (without it, "no message loss" breaks). Secrets = QM admin passwords mounted as files, never in the image or logs.
Migrate without a central team?
App team drives their own migration from the UI: upload CSV, review plan + risk brief, approve at the gate, engine executes. Central team's role shifts to owning the guardrails and the audit. Self-service execution, central governance — weeks to minutes, no control given up.
Token efficiency?
Minimized by design: deterministic engines do the heavy lifting; the LLM gets compact structured inputs and produces language only. Scoped single-purpose prompts, bounded output schemas, fallbacks so we only call it where language adds value. Tens of bounded calls per migration, not a chatty loop.
Security / CHLAUTH? (careful)
Don't volunteer. If asked: "Channel auth is relaxed in this demo environment — a demo choice, not the design." Then future scope: per-peer CHLAUTH (ADDRESSMAP / SSLPEERMAP → MCAUSER, default-block), TLS everywhere (ANY_TLS12_OR_HIGHER), least-privilege MCAUSER, secrets from OpenShift. "The hard part — the governed control plane — is done; security policy slots onto that spine."
RBAC?
Future scope. Today: BCL has the OCP perms it needs; operator identity captured in every audit entry. Next: separate who can plan / approve / execute (separation of duties), scoped per namespace, via the bank's IdP. Foundation's there — we already attribute every action to an actor.
One at a time — why not parallel?
Isolation and rollback stay tractable; one app's failure can't cascade. Right default for critical apps.
NGDC reusability / scale?
Generic control plane; next migration = new CSV. Per-app design scales; SQLite → Postgres, bounded concurrency if needed.
Reliability number — measured?
Reference model (absorbing Markov chain) shown beside the empirical estimate from the real audit log. Never merged.
