01The problem

Enterprise IBM MQ estates consolidate many applications onto a few shared queue managers. That is operationally fragile.

When several applications share one queue manager, they share a failure domain, a maintenance window, a security boundary, and a capacity ceiling. One application's incident becomes everyone's incident. The remedy is to give each application its own dedicated queue manager — but performing that migration on a live estate is the hard part.

A safe migration has to satisfy several constraints at once:

  • No message loss. Every in-flight message must be delivered — none stranded on the old queue, none duplicated.
  • No application change. The producers and consumers cannot be asked to reconfigure connection strings or restart. They must not even notice.
  • No collateral impact. Migrating one application off a shared queue manager must not disturb the other applications still on it.
  • Full auditability. Every change must be recorded — what ran, when, in what order, and whether it succeeded — so the migration can be reviewed and, if needed, reversed.

IntelliAI 2.0 is the control plane that performs this migration while holding all four constraints.

02Our approach

One layer governs every queue manager operation. Nothing touches MQ except through it.

The system is built around a Business Control Layer (BCL) — a single service that is the only component permitted to issue MQSC or talk to the OpenShift cluster. The user interface talks only to the BCL; the BCL talks to MQ. This gives every operation one chokepoint where it can be validated, sequenced, and recorded.

The migration itself is modelled as an explicit state machine, run per application. Each application moves through a fixed sequence of states; every transition emits MQSC and writes an audit record carrying a Lamport clock, so the causal order of events is never ambiguous. If any step fails, the engine rolls that application back — and only that application.

Design stance. Deterministic engines perform every state-changing action — provisioning, rewiring, draining, rollback. Three LLM-backed agents assist the operator with planning, questions, and failure diagnosis. The audit log is the system of record.

03Key capabilities

What an operator can do with the system — and what each capability proves.

Test message flow proves the path

End-to-end message test on any flow: an amqsput places a message, the engine polls the consumer queue depth, and an amqsget retrieves it. It proves a real message travels producer to consumer across the migrated path — not just that the objects exist.

Transparent rewiring no app change

The cutover replaces an app's local queue with a remote-queue alias over an XMITQ bridge. Producers and consumers keep the same connection and queue name — they never reconnect. The migration is invisible to the application.

Blast-radius analysis co-tenants safe

Before a migration runs, the system enumerates every MQSC command it will issue and counts those touching a co-tenant's queues. That count is zero — and the migration is gated on it. Isolation is proven, not assumed.

Per-app rollback clean recovery

If any step fails, the engine reverses that application's completed steps in reverse Lamport order and restores its source queues. Scoped to one app — rolling back app A never touches app B or C.

RCA assistant root cause in seconds

For a failed migration, the RCA assistant reads its Lamport-ordered audit trail, locates the failure event, names the MQ reason code, and produces a structured diagnosis with suggested checks — and answers free-text questions about any migration.

Lamport-clocked audit log everything traceable

Every state change writes one record carrying a Lamport clock, giving an unambiguous causal order of events. The audit log — not the UI, not the LLM — is the system of record.

Evidence export audit-ready

On demand: the exact MQSC script a migration executed, the audit log as CSV, and a per-migration evidence bundle. The work is reviewable after the fact without touching the system.

Reliability model measured, not claimed

An absorbing Markov chain over the state machine gives expected steps to completion and the probability of each outcome — presented alongside an empirical estimate counted from real runs, never merged with it.

05The migration mechanism

How one application's queue moves to a new queue manager without the application noticing.

The migration relies on IBM MQ's own remote-queue routing. The application keeps connecting to the same queue manager and putting messages to the same queue name. What changes is what that name resolves to.

Step one — provision the target

Before any cutover, the BCL deploys the application's dedicated target queue manager as an OpenShift pod and realizes its MQ objects: the dead-letter queue, the application's local queues, and the channel definitions. This is the same provisioning engine used to stand up the source estate, so the target is a known-good queue manager before traffic touches it.

Step two — build the bridge

A transmission path is built between the source and target queue managers:

  • A QLOCAL with USAGE(XMITQ) on the source — the bridge transmission queue.
  • A CHANNEL of CHLTYPE(RCVR) on the target — the receiving end.
  • A CHANNEL of CHLTYPE(SDR) on the source, with XMITQ naming the bridge queue and CONNAME pointing at the target's cluster service on port 1414. The sender and receiver share a channel name, as MQSC requires.

Step three — rewire the queue

For each of the application's queues, the engine runs DELETE QLOCAL followed by DEFINE QREMOTE. The remote-queue alias carries RNAME (the queue's name on the target), RQMNAME (the target queue manager), and XMITQ (the bridge queue). From this moment, a message put to the original name is routed by MQ across the bridge to the target.

Step four — drain and validate

Any messages already sitting on the old local queue at cutover are consumed by the existing consumers. The engine polls the queue depth until it reaches zero — proving no message was left behind — then validates that traffic flows correctly through the new path before marking the application complete.

06Per-app isolation — why other apps are safe

Source queue managers are shared. Migrating one application provably does not disturb the others.

This is the constraint that makes migration genuinely hard, and the one a reviewer will press on. The answer is that the migration is scoped per queue. The rewiring touches only the migrating application's own queues — the co-tenant applications' local queues are never named in any MQSC command the migration runs.

That is not just an assertion. The blast-radius analysis enumerates every MQSC command the migration will issue, before it runs, and counts how many of them touch a co-tenant queue. By construction of the choreography that count is zero, and the analysis confirms it. The migration is gated on that confirmation.

07The migration state machine

Each application moves through a fixed sequence of states. A failure rolls that application back; the operator can then restart it.

Modelling the migration as an explicit state machine — rather than a script — means every application is always in a known, named state, every transition is audit-logged, and recovery is well-defined. The forward path runs nine states from PLANNED to COMPLETED. If any step fails, the engine transitions that application to ROLLING_BACK, undoing its steps in reverse order, and settles at ROLLED_BACK with the failure captured in the audit log. The operator can then restart the migration: the record recycles to PLANNED and the forward path — which is idempotent — runs again from the start.

08The mathematics

Two well-established models, used where they genuinely apply — and cited.

Little's Law — drain-time prediction

At cutover the engine must wait for the old source queue to empty. Rather than poll blindly, it predicts how long that will take. With the producer rewired away, no new messages arrive at the old queue, so the standard queueing relationship reduces to a direct estimate:

L = λW  →  T_drain ≈ L₀ / μ L₀ = observed queue depth at rewire time  ·  μ = consumer service rate, measured from the depth-decrease rate

Reference: Little, J. D. C. (1961). "A Proof for the Queuing Formula: L = λW." Operations Research, 9(3), 383–387. The prediction is surfaced in the UI; the engine still confirms the actual drain by polling depth to zero.

Absorbing Markov chain — reliability model

The migration state machine is analysed as an absorbing Markov chain: COMPLETED, ROLLED_BACK and ROLLBACK_FAILED are absorbing states, the rest are transient. From the transition structure the system computes the standard fundamental-matrix quantities — expected number of steps to absorption, and the probability of ending in each absorbing state.

N = (I − Q)⁻¹ Q = transient-to-transient transition submatrix  ·  N = fundamental matrix, giving expected visits and steps to absorption

Reference: Kemeny & Snell, Finite Markov Chains (1960). The UI presents this reference model alongside an empirical transition estimate counted from the real audit log — model and measurement shown separately, never conflated.

09Components

What each part of the system does, in precise terms.

Deterministic engines

Every state-changing action is performed by deterministic, code-reviewed engines — never by an LLM.

Provisioning engine

Deploys queue manager pods on OpenShift via the Kubernetes API, then realizes their MQ objects — DLQ, local queues, channels — by piping MQSC into the pod. Idempotent: safe to re-run.

MQSC derivation

Pure functions that compute the exact MQSC command set for a topology — queue and channel definitions — with no side effects. The single source of truth for what MQSC a topology requires.

Migration engine

Drives the per-app state machine. Sequences each transition, issues its MQSC, records every step, and on failure delegates to rollback. Resumable and idempotent.

Rewiring choreography

Builds the MQSC for the cutover: the XMITQ bridge, the SDR/RCVR channel pair, and the per-queue QLOCAL-to-QREMOTE swap.

Drain detection

Predicts drain time with Little's Law, then polls the source queue depth to a confirmed zero — the proof that no message was stranded at cutover.

Rollback engine

On failure, walks the application's audit entries in reverse Lamport order and undoes each completed step. Scoped to one application — never touches another.

Agents

Three agents assist the operator, each backed by the Tachyon LLM (Gemini 2.5 Pro).

Migration Planner Agent 1

Produces the per-application migration plan — the ordered step sequence and a plain-language summary the operator reviews before execution.

Operator Assistant Agent 2

Answers free-text operator questions about migration status, the audit trail, rollbacks, and drain predictions. Every answer is drawn from live BCL data.

RCA Assistant Agent 3

Diagnoses a failed migration: reads its Lamport-ordered audit trail, locates the failure event, names the MQ reason code, and produces a structured root-cause report.

Analysis & record

Blast-radius analysis

Enumerates a migration's MQSC ahead of execution and proves the count of commands touching co-tenant queues is zero — the per-app isolation guarantee.

Markov reliability

Computes the absorbing-chain reliability model over the state machine, and an empirical transition estimate from the audit log.

Lamport-clocked audit log

Every state change writes one record carrying a Lamport clock, giving an unambiguous causal order. Held in SQLite — the system of record.

Export endpoints

Produce evidence on demand: the executed MQSC script, the audit log as CSV, a per-migration evidence bundle, and a health summary.

11Honest scope and limits

What this system is, and what it is deliberately not — stated plainly.

  • Channel authentication. Production deployments apply explicit per-peer channel-authentication rules, mapping each authorized partner queue manager to its permitted identity.
  • The reliability figure is a model, not a measurement. The Markov analysis presents a reference model computed from the state machine's structure. It is shown alongside — and never merged with — the empirical estimate counted from real runs.
  • One application at a time. The state machine and rollback are scoped per application by design. This is what makes isolation and recovery tractable; concurrent cross-application scheduling is out of scope for this phase.
  • The audit log is the system of record — not the LLM, not the UI. Every claim the system makes can be traced to a Lamport-ordered audit entry.

In one sentence. IntelliAI 2.0 migrates production IBM MQ applications onto dedicated queue managers using MQ's own remote-queue routing, proves at every step that no message is lost and no co-tenant is disturbed, records everything in a causally-ordered audit log, and recovers cleanly from failure — all driven from a single control plane.
